## 💡 Key insights (méthodologiques)

### I1. **"LLM différent + contexte frais + grep ground-truth" est la règle d'or du cycle review**

3 LLMs successifs peuvent **converger sur la même hallucination** (cf. C1 `OPTIMISTIC_LOCK_VIOLATION` à travers Pass 1/2/3). Le grep ground-truth indépendant est la seule garantie anti-hallucination.

**À codifier CLAUDE.md** : "Pass code-review/validate avec verdict `GO 0 > LOW` doit citer au moins 3 confirmations grep ground-truth (file:line de code merged) pour les patches critiques."

### I2. **Pattern accept_one_X strict (FailedProposal per-proposal) inviolable**

Story 8-5b code-review Pass 1 a détecté un risque latent : les `unreachable!()` aux 4 sites match Rule variants étaient un piège pour futur refactor (crashes Tokio task). Patché vers `tracing::error + AppError::Internal`.

**Pattern** : dans un flow batch (`accept_batch` → `accept_one_invoice/split/rule`), aucune escalade `AppError` global. Toutes les erreurs per-proposal passent par `FailedProposal`. Inviolable et défensif sur les `match` exhaustifs.

### I3. **Audit trail Swiss CO Art. 958f**

Pass 1 code-review HIGH-3 (DELETE race window concurrent reactivate) a souligné l'importance du audit fidelity en software accounting suisse. Pas de "race acceptable" sur audit log — chaque action audit doit reflèter ce qui s'est *réellement* passé.

### I4. **Frontend ReconciliationCandidate discriminator pattern**

Story 8-5b refactor type `candidate_type: Invoice | Rule` avec Option<> fields est réutilisable pour Epic 9+ futures candidates polymorphes (rapports comptables avec différents types de regroupements ?).
