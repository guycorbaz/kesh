   (`DOCKER_START.md`, 1.85) échappe à toute recherche de `1.96` :
   ```sh
   git ls-files -z | grep -zvE '^_bmad-output/|\.pdf$|Cargo\.lock|package-lock' \
     | xargs -0 grep -nIiE 'rust[ :≥>=v-]*1\.[0-9]{2}|rustc [0-9]|rust-1\.'
   grep -rnE '\b1\.96\b' --exclude-dir=target --exclude-dir=node_modules --exclude-dir=.git \
     --exclude-dir=_bmad-output --exclude=*.pdf .
   ```
   **Ensemble admis des occurrences restantes, nommé par ses chemins** : toute ligne rendue par la première commande
   porte `1.97` (ou `rust:1.97`) — sauf `CHANGELOG.md` l. 767 et 785 et `README.md` l. 214 (historiques de la v0.4.0,
   C-31-3-5) et `crates/kesh-api/tests/textes_coherents.rs` (les fixtures de désaccord de G21, AC7, écrivent des
   `rust:1.96-bookworm` à dessein). La seconde commande ne rend que ces mêmes chemins. Tout `_bmad-output/` (fiches,
   rétrospectives, prompts, registres, `sprint-status.yaml`) est exclu : relevés datés. Les PDF se contrôlent aplatis (T5).
2. **AC2 — gate complet vert avec le nouveau clippy.** `scripts/test-fast.sh` (fmt, `clippy --workspace --all-targets
   -- -D warnings`, nextest) vert **sous 1.97.1**, base remise à zéro d'abord (`CLAUDE.md` § *Un gate laisse la base
   piégée*) ; `cargo publish --dry-run -p kesh-import` (étape de la CI, sensible à la chaîne) ; les **quatre** gates
   frontend du `CLAUDE.md` (`npm run check`, `npm run lint-i18n-ownership`, `npm run test:unit`, `npm run build`),
   inchangés par la chaîne Rust mais exécutés au dernier commit de code, comme le veut la règle ; E2E complet :
   **baseline attendue** (`docs/testing.md` § *Les échecs attendus*), à comparer fichier par fichier — le bump ne doit
   changer aucun résultat. Les chiffres réels sont écrits au Dev Agent Record, **seulement ce qui a tourné**.
3. **AC3 — les nouveaux avertissements clippy se corrigent, ils ne se taisent pas.** Chaque lint nouveau déclenché par
   1.97 est **corrigé dans le code**. Aucun `#![allow(...)]`/`#[allow(...)]` nouveau, aucun `-A` ajouté à la CI, sauf
   cas où le correctif change un comportement ou une signature publique : le lint est alors écarté **au site**
   (`#[allow(clippy::x)]` avec commentaire de justification), et chaque exception est inscrite au registre et au Dev
   Agent Record avec le nombre de sites. Un lint **non mécanique** reçoit l'`allow` au site **et** une issue de suivi de
   son correctif (une seule conduite, C-31-3-4) ; l'issue est demandée à l'orchestrateur dans le rapport.
   **Inventaire clos, décidable** : on ne compte que les lignes **ajoutées** (`^\+`), les **attributs** `#[allow(`,
   `#![allow(`, `#[expect(`, `#![expect(` (jamais le `.expect(` d'un `Option`/`Result`), les formes longues et courtes
   en ligne de commande, une table `[lints]`/`[workspace.lints]` et un `clippy.toml` :
   ```sh
   git diff origin/main...HEAD -U0 -- crates Cargo.toml .cargo .config .github Dockerfile frontend/src scripts \
     | grep -E '^\+' | grep -vE '^\+\+\+' \
     | grep -nE '#!?\[(allow|expect)\(|cfg_attr\([^)]*(allow|expect)\(|\[(workspace\.)?lints|clippy\.toml|(^\+|[[:space:]])(-A|--allow)([[:space:]]|[a-z])'
   find . -name '*clippy.toml' -not -path '*/target/*' -not -path '*/node_modules/*'
   ```
   Attendu : zéro ligne, la seconde commande aussi (zéro aujourd'hui) ; sinon, **une ligne par exception inscrite au
   registre**, rapprochée une à une (une ligne retirée n'est jamais comptée : c'est un `-`, filtré). Un avertissement du
   compilateur lui-même (`rustc`, par exemple un lint `unused` ou une dépréciation de la bibliothèque standard) suit la
   même règle.
4. **AC4 — aucune dérive de comportement.** Le diff de production se limite aux correctifs clippy/compilateur de l'AC3,
   mécaniques. Un correctif qui change une valeur, une requête SQL, un message ou un format (sérialisation, PDF, tri)
   n'est pas mécanique : il sort du périmètre et se demande en issue. `Cargo.lock` ne change pas (pas de
   `cargo update`) ; si `Cargo.lock` bouge, c'est un défaut du bump à expliquer.
5. **AC5 — CI verte et image construite.** Au push de la branche (par l'orchestrateur), le job `Backend (Rust)` est vert
   (il tire la chaîne depuis `rust-toolchain.toml`). L'image Docker se **construit** sous le nouveau `FROM` :
   `docker build` local de l'étape `rust-builder` au moins (sous `flock` et `mem-guard`, lourd), et le smoke `/health` du
   workflow de release la contrôlera à la v0.15.0.
6. **AC6 — nettoyage des cibles.** Après le gate, les cibles cargo des worktrees bâties sous 1.96.1 sont supprimées
   (`cargo clean` dans chaque worktree **terminé**, c'est-à-dire dont la branche est mergée ou abandonnée, à l'exclusion
   de tout worktree d'un autre agent encore actif ; **le dépôt principal compte parmi les arbres de travail** mais n'est
   jamais « terminé » : l'orchestrateur le nettoie quand il le décide ; l'orchestrateur désigne la liste, le dev n'y
   touche pas de lui-même ; au 2026-10-23 la station compte 15 arbres de travail, dépôt principal compris, tous sur
   1.96.1), pour ne pas laisser de dizaines de Go d'artefacts périmés. Les toolchains 1.96 et 1.96.1 de la station ne
   se désinstallent pas ici : d'autres branches (celles des stories parallèles) s'appuient sur leur
   `rust-toolchain.toml` tant qu'elles n'ont pas rebasé (C-31-3-3).
7. **AC7 — une garde contre le désaccord `Dockerfile` / `rust-toolchain.toml` (#697, C-31-3-6).** Un test de
   `crates/kesh-api/tests/textes_coherents.rs` (emplacement tranché, C-31-3-8), garde **G21**, repose sur une **fonction
   pure** `rust_versions_accordees(dockerfile: &str, toolchain: &str) -> Result<_, String>` dont la règle est complète :
   - **Dockerfile** : lignes `^\s*FROM\s+rust:` **non commentées** (une ligne `# FROM rust:…` n'existe pas), `FROM`
     **sans égard à la casse** (une instruction Dockerfile l'est, `dockerfile_fixe` normalise de même — validation P3,
     R3) ; **exactement une** (zéro ou deux → rouge explicite) ; le tag doit être `X.Y[.Z]`, suivi ou non de
     `-<suffixe>` (`rust:1.97-bookworm`, `rust:1.97.1-bookworm`, et `rust:1.97`, tag valide sur Docker Hub — validation
     P3, R3/F4) et peut être suivi de `AS <nom>` ; un tag sans mineur (`rust:1-bookworm`, `rust:bookworm`,
     `rust:latest`) → rouge explicite.
   - **`rust-toolchain.toml`** : ligne **non commentée** `channel = "X.Y"` ou `"X.Y.Z"`, guillemets doubles **ou simples**
     (chaîne littérale TOML) ; une ligne `# channel = …` n'existe pas ; exactement une (deux → rouge explicite) ; un
     `channel` non numérique (`stable`, `nightly`, `beta`) ou absent → rouge explicite (validation P3, F4).
   - **Comparaison** : les mineures `X.Y` sont égales ; si **les deux** portent un patch, les patchs sont égaux aussi
     (`rust:1.97.0` contre `channel = "1.97.1"` est refusé) ; si un seul en porte un, le patch n'est pas comparé
     (convention du tag mineur, C-31-3-2).
   **Rouge d'abord** : les cas de la fonction pure sont écrits et constatés rouges **avant** que la garde ne lise le
   dépôt — accord (`rust:1.97-bookworm` / `1.97.1` ; `rust:1.97.1-bookworm AS rust-builder` / `1.97.1` ; `1.97` /
   `"1.97"`) ; désaccord de mineure (`rust:1.96-bookworm` / `1.97.1`) ; désaccord de patch (`1.97.0` / `1.97.1`) ; zéro
   ligne `FROM rust:` (dont la seule ligne commentée) ; deux lignes `FROM rust:` ; tag sans mineur ; `channel =
   "stable"` ; `channel` absent ; deux lignes `channel` ; `channel` commenté seul (→ absent) ; `channel = '1.97.1'`
   (accord) ; `rust:1.97` sans suffixe (accord) ; `from rust:1.97-bookworm` en minuscules (accord). **Positives adossées** : le test du dépôt vérifie que les deux versions ont bien été
   extraites (un motif qui ne trouve rien est un vert muet) et que la fonction rend `Ok`. **Mutation** : remettre le
   `Dockerfile` à `rust:1.96-bookworm` doit faire rougir G21 (et elle seule, `dockerfile_fixe` de
   `configuration_transmise.rs` ne lisant que l'étape finale) ; la mutation par `rust-toolchain.toml` → 1.96.1 recompile
   tout sous l'ancienne chaîne, on préfère celle du `Dockerfile`. Le tableau d'en-tête du fichier reçoit la ligne G21.
   La PR porte `closes #697` (dans le corps de la PR, pas dans un commit).
